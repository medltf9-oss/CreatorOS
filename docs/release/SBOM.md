# v1.0.0 software bill of materials

`scripts/generate_sbom.py` writes a CycloneDX 1.5 JSON document from artifacts that exist in this
checkout. It is a machine-readable inventory of what was inspected, not a legal opinion. The release
gate's SBOM checks and this document are described in the sections below.

## Three profiles, three claims

One document cannot honestly describe the checkout, the tools a user installs separately, and the
installer bytes at the same time. The generator therefore has three profiles; `all` remains for
backwards compatibility but is not used by the release gate.

| `--profile` | Describes | Generated by | Gate |
| --- | --- | --- | --- |
| `source` | This checkout: the two application components, direct Node dependencies from the lockfile, and Python distributions from the committed `app/backend/requirements-runtime.lock`. No virtualenv, no `node_modules`, no external tools and no installer binding. | `release-gate.ps1 -Stage Source` when absent, or `build-release.ps1` | `release.sbom.source` |
| `prerequisites` | External tools the user acquires separately: `ffmpeg`, `ffprobe` (hashes and licence/redistribution status declared in `DEPENDENCY_MANIFEST.md`) and `ollama` from the prerequisites manifest. It never reads a downloaded binary, so it is reproducible before those tools exist. | `release-gate.ps1 -Stage Source` when absent, or `build-release.ps1` | `release.sbom.prerequisites` |
| `artifact` | The packaged payload actually inside the installer (`releases/<v>/win-unpacked/resources/backend`) plus the installer's SHA-256 and size on `metadata.component`. Every Python distribution is read from the payload's own `METADATA`/`RECORD`, not from the builder venv. This is the only profile that may be used as artifact provenance. | `build-release.ps1` after packaging | `release.sbom` and `artifact.sbom` |

The source and prerequisite documents are regenerated by the gate when missing. The artifact
document is never generated by the gate: it must hash the installer that is actually being released.

## What the document covers

| Component(s) | Source read by the generator |
| --- | --- |
| `CreatorOS` product component | `--version`, or `app/desktop/package.json` when omitted |
| `creatoros-desktop` (application) | `app/desktop/package.json` version, Apache-2.0 detected from `LICENSE` |
| `creatoros-backend` (application) | `app/backend/pyproject.toml` `[project] version`, Apache-2.0 from `LICENSE` |
| Node direct dependencies | `app/desktop/pnpm-lock.yaml` `importers['.']`: `dependencies` are `required`, `devDependencies` are `excluded` with a `creatoros:scope-reason` saying they are build-time only. Exact versions and SRI integrity come from the lockfile; licences come from the committed `app/desktop/third-party-licenses.json`, never from `node_modules`. A peer suffix is preserved in `creatoros:lockfile-resolution` |
| Python distributions (`source`) | `app/backend/requirements-runtime.lock`, the committed marker/extra-aware closure. Each component records `creatoros:version-source=backend-lock` and a `pkg:pypi/name@version` purl. A missing or malformed lock is a hard failure; there is no venv fallback |
| Python distributions (`artifact`) | The packaged payload's `Lib/site-packages/*.dist-info/METADATA` and `RECORD`. Membership and versions must match the runtime lock and `pyproject.toml`; development-only and unowned files are rejected |
| `ffmpeg` and `ffprobe` | `source` profile: omitted. `prerequisites` and `artifact` profiles: version, SHA-256 and licence/redistribution status declared in `docs/release/DEPENDENCY_MANIFEST.md`, without reading a binary. The legacy `all` profile still hashes the real `tools/ffmpeg/bin/*.exe` and compares it with the manifest |
| `ollama` | Only when `--prerequisites` names a manifest that declares it (version, byte size, SHA-256, expected signer subject) |

Every component has a `bom-ref` and, where a package identity exists, a purl (`pkg:npm/...` or
`pkg:pypi/...`). Hashes in `hashes[]` are SHA-256, lowercase hex. Node packages are not hashed: the
lockfile records a sha512 SRI of the registry tarball, which is preserved as a property rather than
converted into a hash of a file this repository does not have.

### Packaged-payload provenance

`--profile artifact` requires both `--artifact` and `--payload`. For every distribution in the payload
it verifies the `RECORD` size and SHA-256 of each shipped file, rejects unsafe or escaping paths,
rejects development-only distributions and files that no `RECORD` owns, and requires exactly one
first-party `creatoros-backend` dist-info whose version equals `pyproject.toml`. Two classes of
`RECORD` rows are recorded rather than treated as payload failures:

- `../../Scripts/*.exe` console wrappers: outside the payload, not shipped, counted in
  `creatoros:external-console-scripts-not-shipped`;
- a compiled accelerator (`.pyd`) that is absent while the distribution's own pure-Python module of
  the same name is present: counted in `creatoros:optional-compiled-extensions-absent`, with an
  explicit reason property. A missing `.pyd` without a fallback remains a hard failure. On the SAC
  audit machine the eight SQLAlchemy accelerators are quarantined this way; the payload runs the
  pure-Python implementation and the absence is recorded, not hidden.

The document also binds the payload tree: `creatoros:payload-tree-sha256` is SHA-256 over the
lexicographically POSIX-path-sorted lines `<relative-path>\0<file-sha256>\n`, with
`creatoros:payload-files` and `creatoros:payload-bytes`. `scripts/runtime-inventory.py` computes the
same digest independently and `build-release.ps1` fails if the two disagree.

### Reproducibility

The source profile reads only committed inputs (`pnpm-lock.yaml`, `third-party-licenses.json`,
`requirements-runtime.lock`, `pyproject.toml`, `package.json`, `LICENSE`). The serial number is a
UUIDv5 over the canonical sorted component list; it does not depend on the checkout path, the
virtualenv, `node_modules`, wall-clock time or component order. `build-release.ps1` and
`release-gate.ps1` pass the source commit time as `--timestamp`, so the same commit produces the same
source and prerequisite documents byte-for-byte in any clean clone.

Components are sorted by `(type, name, version)` and JSON is written with a fixed indent and LF
newlines, so the same inputs produce the same bytes apart from `metadata.timestamp`. Without
`--serial`, the serial number is a UUIDv5 over the sorted component list; it changes exactly when a
component changes and not when the clock changes. `--timestamp` and `--serial` make a run fully
reproducible.

## Generate

From the repository root, using the backend virtual environment:

```powershell
cd D:\CreatorOS
$py = 'app\backend\.venv\Scripts\python.exe'
$pre = 'app\backend\src\creatoros\resources\prerequisites.v1.json'

& $py scripts\generate_sbom.py --profile source --version 1.0.0 `
  --output releases\1.0.0\sbom-source.cdx.json --check
& $py scripts\generate_sbom.py --profile prerequisites --version 1.0.0 `
  --prerequisites $pre --output releases\1.0.0\sbom-prerequisites.cdx.json --check
& $py scripts\generate_sbom.py --profile artifact --version 1.0.0 `
  --prerequisites $pre --artifact releases\1.0.0\CreatorOS-Setup-1.0.0.exe `
  --output releases\1.0.0\sbom.cdx.json --check
```

`scripts\build-release.ps1` runs all three after it writes `SHA256SUMS.txt`. The source and
prerequisite documents are also what `release-gate.ps1 -Stage Source` generates when they are absent,
which is how a clean clone reaches a green Source stage without a prebuilt installer.

`--artifact` binds the document to the bytes being released: it records the installer's SHA-256
and size on `metadata.component.hashes` and `creatoros:artifact-*` properties. The Artifact gate
(`artifact.sbom`) fails unless that hash equals the installer on disk, so an SBOM generated before
the final build cannot be reused as provenance for it. `scripts\build-release.ps1` runs this step
after it writes `SHA256SUMS.txt`, so the manifest, the SBOM and the installer all describe the same
bytes.

### Clean clone

The Source stage is reproducible from a fresh clone after the documented bootstrap:

```powershell
git clone https://github.com/medltf9-oss/CreatorOS.git CreatorOS-clean
cd CreatorOS-clean
powershell -ExecutionPolicy Bypass -File scripts\bootstrap.ps1
powershell -ExecutionPolicy Bypass -File scripts\release-gate.ps1 -Stage Source -ReleaseVersion 0.8.0
```

`bootstrap.ps1` creates `app/backend/.venv`, installs the backend package and runs `pnpm install`.
The gate then generates the source and prerequisite SBOMs itself. A bare checkout without those
dependencies cannot produce a truthful dependency inventory: the generator records
`creatoros:collection-error` and the gate fails rather than passing a document that omits the
environment.

The procedure is reproducible, but the Python inventory is only as exact as the backend
environment: `app/backend/pyproject.toml` has no lockfile, so a fresh install can resolve different
patch versions over time. Node versions are pinned by `pnpm-lock.yaml`. A backend lockfile is an
open reproducibility item; until it exists, reviewers must compare the source SBOM component list
between the build machine and the release record, and the artifact SBOM remains the authoritative
inventory of shipped bytes.

Naming a missing manifest is a required-input error (exit 2). The generator never downloads anything:
it only reads local files and runs the FFmpeg binaries with `-version`.

`--check` re-reads the file just written and exits 1 with a list of structural problems: missing
top-level fields, duplicate `bom-ref`, a component without a name or type, a malformed hash, an
application component without a version, or no components. Exit code 2 means a required input was
missing or unreadable (desktop `package.json`, backend `pyproject.toml`, `pnpm-lock.yaml`, an
explicitly passed `--prerequisites` file, or an invalid `--timestamp`/`--serial`). A missing FFmpeg binary, an unreadable FFmpeg banner, an
absent `.venv`, or incomplete Ollama metadata do not fail the run; each is recorded in
`creatoros:collection-error` properties so the gap is visible in the document itself.

### Prerequisites manifest format

The generator reads the same pinned document the first-run wizard verifies against:
`app/backend/src/creatoros/resources/prerequisites.v1.json` (schema `creatoros.prerequisites.v1`).
From its `components` list it takes the entry whose `id` is `ollama` and records
`version`, `acquisition.size_bytes`, `acquisition.sha256` (lowercased) and
`signature.expected_subject`.

```json
{
  "schema": "creatoros.prerequisites.v1",
  "components": [
    {
      "id": "ollama",
      "version": "0.40.18",
      "acquisition": {
        "size_bytes": 1953587080,
        "sha256": "ad2bb47aa969b21cf8dd81b2d9f9a6d5030270ed242ef55087118c37c510acc2"
      },
      "signature": { "expected_subject": "CN=Ollama Inc., O=Ollama Inc., L=Toronto, S=Ontario, C=CA" },
      "license": { "name": "MIT for Ollama" }
    }
  ]
}
```

A missing `version` or SHA-256 is a hard error; a missing size or signer subject becomes a
`creatoros:collection-error`. `license.spdx` is used when present and `license.name` otherwise; a
non-SPDX name such as `MIT for Ollama` is not converted into a licence identifier, so the component
records `creatoros:license-status=unknown`. The older flat `{"ollama": {...}}` shape is still accepted,
and a document with any other `schema` value is refused rather than silently ignored. This file is an
input, not a grant of redistribution rights. A version or SHA-256 that disagrees with the repository's
`DEPENDENCY_MANIFEST.md` is recorded as a collection error.

## How the release gate consumes it

At the **Source** stage the gate validates `releases\<version>\sbom-source.cdx.json` and
`releases\<version>\sbom-prerequisites.cdx.json`. It generates either document when it is absent,
using the backend virtual environment (or `python`/`py` on `PATH`). Both documents must pass the
common checks:

- `bomFormat` is `CycloneDX` and `specVersion` is `1.4`, `1.5` or `1.6`;
- `metadata.component.version` equals the gate's `-ReleaseVersion`;
- `serialNumber` is a real `urn:uuid` (a zero or placeholder serial is rejected);
- `metadata.timestamp` parses, is not in the future and is at most 30 days old;
- every component has a non-empty `name`, `version` and `type`, and no `bom-ref` appears twice;
- no component carries a `creatoros:collection-error`.

The source document must contain `creatoros-desktop` and `creatoros-backend`. The prerequisite
document must contain exactly one `ffmpeg` and one `ffprobe`, each with a SHA-256, and every
prerequisite component must carry a SHA-256 and a licence (or an explicit `creatoros:license-status`).

At the **Artifact** and **Release** stages the gate looks for `sbom.cdx.json`, `sbom.spdx.json` or
`docs\release\sbom-<version>.cdx.json` and requires the chosen document to be a valid artifact
profile: its `metadata.component.hashes` must contain the exact SHA-256 of the installer being
released (`artifact.sbom`). That is what makes the document evidence for an artifact instead of
provenance for a build: regenerating the SBOM is required whenever the installer changes. The gate
does not verify licences or the truth of supplier fields; those are the generator's and the
reviewer's job. `--check` remains part of the release procedure: run it, keep its exit code 0, and
attach the same file the gate will read. Do not hand-edit the document to satisfy the gate.

Two further gates in the same stage validate the prerequisites manifest itself:
`release.prerequisites` checks schema, ids, https-only downloads, positive sizes, 64-hex digests,
boolean signature/redistribution flags and consent, and `release.prerequisites-hashes` requires every
pinned digest to appear in `DEPENDENCY_MANIFEST.md`.

## Regenerate after any payload change

Regenerate and re-run `--check` before every tagged build, and again if any of these change:

- `app/desktop/package.json` or `app/desktop/pnpm-lock.yaml` (including a `pnpm install`);
- `app/backend/pyproject.toml`, or the installed set in `app/backend/.venv` (`pip install`, `pip
  uninstall`, an interpreter change);
- `LICENSE`;
- any file under `tools/ffmpeg/bin` (a different FFmpeg build must produce a different hash and
  banner version);
- the prerequisites manifest used for Ollama.

A serial number that changes between two runs means the component list changed; review the diff
before publishing. A serial number that stays the same while files were rebuilt means the recorded components,
versions, hashes and properties are unchanged, which is itself worth confirming.

## Current repository facts

- The source version is 0.8.0 (`app/desktop/package.json` and `app/backend/pyproject.toml`). Passing
  `--version 1.0.0` labels the product component; it does not change the two application component
  versions, which stay tied to their real source files until those are bumped. The
  generator records `creatoros:desktop-package-version` on the product component when the requested
  release version and the desktop version differ.
- FFmpeg is GPLv3 and the dependency manifest marks it **Blocked for bundling**. The SBOM repeats
  that status and does not upgrade it.
- Ollama's installer is signed and hash-verified but **not approved for v1.0.0 bundling yet**; it is
  included only when a prerequisites manifest declares it, as an excluded component.
- The backend virtual environment contains packaging and test tooling (for example `pyinstaller`,
  `pytest`, `pip`). Components not reachable from declared runtime or dev dependencies are marked
  `excluded` with a scope reason instead of being presented as shipped runtime dependencies.
- If the editable install metadata for `creatoros-backend` is stale (it currently reports 0.1.0 while
  `pyproject.toml` declares 0.8.0), the generator still uses the pyproject version and does not emit a
  second, conflicting backend component.

## What the document does NOT prove

- It is **not a legal review**. It records what the repository says about licences; it does not
  determine obligations, compatibility, or whether a licence claim is correct.
- It is **not provenance** for unverified binaries. A SHA-256 proves which bytes were on this machine
  when the file was read; it does not prove who built the binary, that it was signed, or that it is
  safe. FFmpeg is unsigned and Ollama's signer is only recorded, not verified here.
- It contains **no model weights**, user media, databases, credentials, or files under `models/`,
  `data/` and `logs/`.
- It does **not guarantee licence compatibility** between bundled components or with the product's
  Apache-2.0 licence.
- It does **not** list transitive Node dependencies. Only `importers['.']` direct dependencies are
  recorded; the lockfile remains the authority for the full tree.
- It does **not** hash installed Python distributions, the CPython interpreter payload, Electron,
  Node, or any file that is not explicitly listed above.
- It does **not** prove that the tested `.venv` or the recorded FFmpeg build is what an installer
  ships. The installer payload must be audited separately.

## Maintenance

The generator is standard-library-only Python 3.12. Its tests call the script by path and assert
against the real repository:

```powershell
cd D:\CreatorOS\app\backend
.\.venv\Scripts\python.exe -m pytest tests/test_release_sbom.py -q
.\.venv\Scripts\python.exe -m ruff check ..\..\scripts\generate_sbom.py tests\test_release_sbom.py
```

Only `app/backend/pyproject.toml` carries a `[tool.ruff]` section (`line-length = 110`). `scripts/`
is outside that configuration root, so ruff applies its default/global settings there; keep the
generator within 110 columns anyway.

## 3. Migration `f6a7b8c9d0e1` on a real database

(`data/backups/manual-p6-20261122T235145Z.db`) and upgraded in place:

```
#       account capabilities, OAuth sessions and refresh journal
```

```
head: f6a7b8c9d0e1 · tables: 40 · fk: [] · integrity: ok · agents: 111 · accounts: 0
provider_app_config columns: provider, route, client_id, client_secret_ref_id, redirect_uri,
  scopes_json, api_version, app_mode, login_config_id, notes, last_verified_at, id, created_at,
  updated_at
```

Reversibility, verified on an **isolated copy** (`CREATOROS_ROOT=<DATA_ROOT>\temp\p6root`, so the
live database is not touched):

```
copy head:        f6a7b8c9d0e1   tables: 40
alembic downgrade -1
after downgrade:  c4a91f7d2b60   tables: 37   fk: []
alembic upgrade head
re-upgraded:      f6a7b8c9d0e1   tables: 40   fk: []   integrity: ok   agents: 111
```

**Note, stated because it happened:** a downgrade drops the columns the migration added, so any
Phase-6 state stored in them is lost. Point alembic at a copy (`CREATOROS_ROOT=…`) when testing a
downgrade; back up before migrating a live database. The SQLite file must be copied together with
`-wal` and `-shm`, or the copy silently misses the most recent commits (this was observed: a
`.db`-only copy reported the pre-migration head).

the secret before deleting the row, with two new tests
(`test_deleting_an_app_revokes_its_secret`, `test_api_delete_removes_the_vault_record`) and verified
in the running app: after **Delete app**, `vaultHealth().entries == 0`, provider apps `0`,
`config/secrets` empty.

Clean-up afterwards: the test rows were removed; the database holds 0 provider apps, 0 accounts,
0 `secret_ref` rows, 1 cancelled OAuth session, and the audit trail of what happened.

## 7. What the tests prove (and how)

| Claim | Evidence |
| --- | --- |
| No secret is ever stored in the database | `test_social_leaks.py` scans the SQLite file byte for byte for six needles after a full claim, refresh and disconnect |
| No secret appears in an API response | same file, every social response body scanned incl. error bodies |
| No secret reaches the log or the audit table | `test_no_secret_in_logs_or_audit`, `test_audit_events_record_references_not_values` |
| The vault refuses tampered records | `vault.test.cjs`: single-byte flip and truncation → `VAULT_CORRUPT`, record preserved |
| The broker cannot be enumerated | `vault.test.cjs`: no list/bulk route, wrong purpose → refused, 121st request in a minute → 429, 16 KiB+ body destroyed |
| State replay cannot succeed | `test_social_oauth.py`: two concurrent callbacks, one wins, the other gets `STATE_CONSUMED` |
| TikTok refresh survives an interruption | `test_social_tokens.py`: conditional lock, stale-lock takeover, `resolve_interrupted` decides from stored facts |
| Instagram's two paths are never merged | `test_social_instagram.py` + `test_social_accounts.py`: separate rows, duplicates recorded as observations |
| Capabilities are explainable | `test_social_capabilities.py`: every state reachable, reason text asserted, legacy strings normalized |
| Agents cannot touch secrets | `test_agent_social_tools.py`: two read-only tools, no secret field, implementation free of vault/network calls |
| The migration is reversible | `test_social_migration.py` + the isolated-root round trip in §3 |

## 8. Honest limits

* **No live provider account is connected.** No Meta or TikTok developer app exists on this machine,
  so the browser round trip could not be completed and no real token was ever obtained. Every HTTP
  shape in the tests comes from `httpx.MockTransport` fixtures recorded from the published docs, and
  the tests say so. The only real provider calls in the product are *Verify now* and *Run
  diagnostics* on a connected account — they need a real account to exist.
* **DPAPI protects against other Windows users and offline disk access, not against malware running
  as this user.** Stated verbatim in the GUI and in `CREDENTIAL_VAULT.md`.
* **Instagram Business Login has no revoke endpoint.** Disconnecting deletes the credential here and
  says so; `revoked_at_provider` stays `false`.
* **Facebook has no refresh token.** `can_refresh` is `false` for a Page token and the button is
  disabled with the reason.
* **`read_insights` / `instagram_business_manage_insights` need app review** and are not requested at
  connect time; both capabilities are reported `requires_developer_approval` with
  `headline=false`.
* **TikTok Direct Post needs the add-on**; login succeeding never implies it.
* **Publishing does not exist.** `publishing: not_implemented`, no publish/upload/post code path, and
  the TikTok adapter's only POST is a read-only `creator_info` query.
* **NVENC remains unusable on driver 582.78** (Phase 5 finding, unchanged).

## 9. Phase 7 readiness

Ready to build publishing on:

* `POST /social/accounts/{id}/capabilities` verdicts answer "may this account do X?" with a reason;
* `TokenService.access_token(account)` returns a live token, refreshing first, and fails with a typed
  code that says whether the user or the provider must act;
* accounts, app registrations and credentials are addressable by stable ids;
* the vault hands out exactly one value per scoped call;
* `publish_capable_accounts` in `/social/overview` is the query Phase 7 can start from.

Still needed before anything can actually publish:

1. a Meta developer app (Facebook Pages + the Instagram paths you intend to use) and a TikTok app,
   registered per `DEVELOPER_APP_SETUP.md`;
2. at least one connected account, so capabilities are real;
3. app review for the publish scopes, or `development` mode with test users;
4. the publish implementations themselves (Phase 7), with human approval gates.

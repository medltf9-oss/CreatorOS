## B. Built and verified only as artefacts (cannot be executed here)

| Claim | What exists | Why it cannot run here |
| --- | --- | --- |
| The NSIS installer installs, creates shortcuts and can be uninstalled | `releases\0.8.0\CreatorOS-Setup-0.8.0.exe` + the generated NSIS script incl. `build/installer.nsh` | **Smart App Control is ON** on this machine and refuses every newly built unsigned executable (`CodeIntegrity 3077`, "did not meet the Enterprise signing level requirements"; `cmd.exe` gets "blocked by Device Guard policy"). Two earlier builds of the same installer did run and produced the 17/17 result above; later builds are refused. The block is a property of the *build's signature*, not of the installer |
| A signed build would install normally | `electron-builder.yml` reads `CSC_LINK`/`CSC_KEY_PASSWORD`; ADR-34 says which two flags to flip back | no code-signing certificate exists for this project |

The fallback that *is* verified here: `scripts/install-unpacked.ps1` produces the identical layout,
shortcuts and "Installed apps" entry without the NSIS wrapper, and `scripts/uninstall-unpacked.ps1`
reverses it. That is how the installed-app screenshots above were taken.

## D. Deliberate decisions worth re-reading later

* The shipped `CreatorOS.exe` is **byte-identical** to the vendor `electron.exe` (`sha256` equal), so it
  carries Electron's embedded icon and version metadata. The brand is applied where a user sees it —
  shortcut icon, window icon, installer artwork — instead of by patching a signed binary and losing its
  signature. ADR-34 records the trade and what changes when the project can sign.
* The shipped backend is an **interpreter bundle**, not a frozen executable, for the same reason. It is
  40 MB larger and starts in ~2 s instead of ~1 s, and it is the only layout that runs on this machine
  without changing a Windows security setting.
* `scripts/verify-install.ps1` polls for the uninstaller to finish. A silent NSIS uninstall returns
  before its work is done; sampling once at 3 s reported a failure for a deletion that was still in
  flight, which is exactly the kind of false negative that teaches people to ignore a test.

**Smart App Control.** With `VerifiedAndReputablePolicyState = 1`, Windows refused the freshly built
stub at process creation (CodeIntegrity 3118, "application control policy has blocked this file");
because electron-builder executes that stub to generate the uninstaller, packaging itself failed at
`computeScriptAndSignUninstaller` with `spawn UNKNOWN`. The machine owner then turned Smart App Control
off (`VerifiedAndReputablePolicyState = 0`); packaging and installation succeeded on the next attempt.
This is recorded because it is the difference between "the installer works" and "the installer works
when the machine does not enforce SAC".

**Additional observations from the same run**

* A silent install (`CreatorOS-Setup-0.8.0.exe /S`) exited 0 and produced exactly the layout above.
  The installer window itself was captured: French system locale, "Juste pour moi (the current user)"
  preselected, "Pour tous ceux qui utilisent cet ordinateur" marked as requiring administrator.
* Launching the installed app normally started its bundled backend from
  `%LOCALAPPDATA%\Programs\CreatorOS\resources\backend\python.exe`; the data root contained
  `data\database\creatoros.db`, `logs\backend\*.log` and `temp` after the first launch.
* Theme persistence was measured in the installed app: toggle dark → light, close the window (backend
  child exits too), relaunch, and the shell comes back in light mode from
  `localStorage['creatoros.theme']`.
* **`ELECTRON_RUN_AS_NODE=1` inherited from the parent**: the installed exe exits with code 9 and
  never opens a window. Electron itself runs as Node in that mode, so the app cannot sanitize its own
  startup; the launcher scripts and the Windows shortcut do not set the variable, and README documents
  the fix. Launching with the variable unset works. This is a documented host-environment limit, not a
  control that silently fails.
* **Not tested:** a second Windows user, a clean Windows installation, or a machine with Smart App
  Control left on. All three need an administrator (create a user / reset the VM / reboot with SAC
  enforced), which this session does not have. The fresh-data-root runs above are *not* a clean-machine
  test and are not reported as one.

# Phase 10 evidence

Phase 10 is about proving things rather than building them, so the evidence file is the deliverable that
matters most. It keeps the four classifications of `docs/LIVE_PROVIDER_VERIFICATION.md` strictly apart:

* **Implemented** - the path exists and is reachable.
* **Fixture tested** - a test drives it with a mocked provider.
* **Real provider tested** - a live call reached the provider and the answer is recorded here.
* **Blocked** - an external grant, credential or approval this machine does not have.

At the end of Phase 10 there is **no real-provider row**: this machine has no Meta app, no TikTok app, no
connected account, no delivery bucket and no code-signing certificate. Every "blocked" line below is a
fact about the installation, not a defect, and `scripts/activation_status.py` prints the same thing.

---

## A. The verification harness, proven end to end over HTTP

`scripts/live_verify.py` was run against a **separately booted backend** (`uvicorn` on `127.0.0.1:5799`,
a throwaway data root under `temp/lv`, migrations at `b8c9d0e1f2a3`), with one Facebook account seeded
directly into that database so that the steps had something to talk about. The vault broker was *not*
running, which is exactly the state a headless start produces - and the harness said so instead of
guessing.

```
 1. OAuth connection                 BLOCKED  the account is unknown
 2. Account discovery                BLOCKED  provider refused: the credential vault is not available:
                                              the backend was started outside the desktop shell
                                              (no broker URL or token was provided)
 3. Permission verification          BLOCKED  the provider did not return a scope list
 4. Capability snapshot              OK       4 of 5 capabilities available
 5. Token lifecycle                  BLOCKED  the stored credential cannot be read: access_token VAULT_UNAVAILABLE
 6. Analytics synchronisation        BLOCKED  2 metric(s) attempted, none observed - see the per-metric
                                              reason on the availability panel
 7. Media delivery                   BLOCKED  not configured: bucket configuration, credentials
 8. Publishing preflight             SKIPPED  no --destination given
 9. Human approval                   SKIPPED  no --destination given
10. Real provider publication        SKIPPED  no --destination given
11. Remote status reconciliation     SKIPPED  no --destination given
12. Analytics for published content  SKIPPED  no --destination given

RESULT: verification incomplete - the blocked steps need a grant, credential or approval
```

| What this proves | Why it is worth recording |
| --- | --- |
| the harness really talks HTTP, not an in-process shim | it ran against a second process on a different port |
| a missing credential is reported as `blocked` with the code | step 5 reads `secret_health`, not just the stored token state |
| a metric that could not be read is **not** a zero | step 6 reported `2 attempted, none observed` with a pointer to the reason |
| unconfigured delivery is named, with its missing fields | step 7 printed `bucket configuration, credentials` |
| steps 8-12 do not run without a destination | they printed `skipped`, not a pass |
| the exit code reflects incompleteness | `1`, not `0` |

The run also found one real defect in the harness itself, fixed in the same milestone: step 5 originally
trusted `GET /social/accounts/{id}/token`, whose state is a pure function of stored facts, and therefore
reported "token valid" while the vault could not decrypt the credential at all. It now cross-checks
`secret_health` and reports `BLOCKED`.

The opt-in gate was verified too: with `CREATOROS_LIVE_VERIFY` unset the harness prints
`refused: CREATOROS_LIVE_VERIFY=1 is not set; this harness talks to real providers` and exits `2`, and an
unreachable API is reported as `cannot reach <base>: ...` rather than a stack trace.

## C. Code signing

`scripts/sign-release.ps1 -Check` (report only, exit 0):

```
  Smart App Control : enforced (ON)
  signtool          : C:\Program Files (x86)\Windows Kits\10\bin\10.0.26100.0\x64\signtool.exe
  CSC_LINK          : none
  CSC_KEY_PASSWORD  : not set
  timestamp server  : reachable: http://timestamp.digicert.com
  current signatures:
    CreatorOS-Setup-0.8.0.exe        NotSigned    no timestamp   n/a
    CreatorOS.exe                    NotSigned    no timestamp   n/a
```

`-Verify` exits 1 (`1 artefact(s) are not validly signed`). `-Sign` refuses with
`CSC_LINK is not set: there is no certificate to sign with`.

The signing path itself is proven with a throwaway certificate (`-SelfTest`), on a **copy** of the real
installer under `%TEMP%`, which is then deleted along with the certificate:

```
  before: NotSigned / no timestamp
  after : UnknownError / timestamped - signer CN=CreatorOS Self-Test (throwaway)
  chain : UntrustedRoot
  tampered copy: HashMismatch
SELF-TEST PASSED: signing, verification, chain building and tamper detection all work.
```

Two measured findings, both recorded in `docs/CODE_SIGNING.md` and in an ADR-34 correction:

* the Electron binary that npm installs is **not** Authenticode-signed
  (`Get-AuthenticodeSignature electron.exe` = `NotSigned`), and `win-unpacked\CreatorOS.exe` is
  byte-identical to it (both `sha256 a547b53f…`). Phase 9's premise that the packaged app keeps a vendor
  signature was wrong; nothing is overwritten by signing it.
* the same unsigned installer that Smart App Control refused in Phase 9
  (`sha256 0ac5865c…`) installed in Phase 10 (see section D). The decision is not deterministic, which
  is an argument for signing, not against it.

Everything provider-facing. `scripts/activation_status.py` at the end of Phase 10:

```
Facebook / Instagram / TikTok logins   MISSING   no registered developer app
Media delivery                         MISSING   no S3-compatible provider
Analytics                              READY     nothing scheduled yet
```

No social account exists, no publication has been made, and no analytics observation has been collected
from a provider. `docs/LIVE_PROVIDER_VERIFICATION.md` §3 is the procedure that would change that, and
`docs/evidence/P10.md` will gain a real-provider section the day it runs.
